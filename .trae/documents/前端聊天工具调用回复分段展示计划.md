# 前端聊天工具调用回复分段展示计划

## Summary

- 目标：将前端聊天页当前“思考内容 / 工具调用 / 正文 / 执行详情”并列展示的方式，改为“按回复切段”的链式展示。
- 目标展示规则：
  - 有回复时：`思考1 + 工具调用1（包含在思考1内） + 回复1 + 思考2 + 工具调用2（包含在思考2内） + 回复2 ...`
  - 无回复时：所有内容继续留在思维链中展示，不提前新开回复块。
  - 只有在出现过回复后，后续新的思考链才允许单独新开一个思维链块。
- 已确认的产品决策：
  - 现有“工具与执行详情”并入思维链，不再作为独立重复区域展示。
  - 回复边界按“相邻两次工具调用之间的正文合并”为一个回复段，而不是按每个 chunk 切碎。

## Current State Analysis

### 现状落点

- `frontend/src/features/chat/ChatPage.tsx`
  - 负责消费流式事件。
  - `chunk` 事件仅通过 `updateLastMessage(content, reasoning)` 直接把正文和 `reasoning_content` 追加到最后一条 assistant 消息。
  - `tool` / `plan` / `task` / `result` / `subagent_*` 等事件被收敛进 `messageMeta[messageId]`，没有和正文建立“分段边界”关系。
- `frontend/src/features/chat/store/chatStore.ts`
  - `ChatMessage` 仅保存 `content`、`reasoning_content`、`toolEvents`。
  - `updateLastMessage()` 的语义是“直接追加最后一条 assistant 消息字符串”，没有段级结构。
- `frontend/src/features/chat/components/ChatMessage.tsx`
  - 目前固定顺序渲染：
    - `ReasoningContent`
    - `InlineToolCallCard[]`
    - `MessageContent`
    - `AssistantExecutionDetails`
  - 这会把同一轮里的工具调用和回复拆成平级区块，而不是按“思考链 -> 回复”成组展示。
- `frontend/src/features/chat/components/ReasoningContent.tsx`
  - 当前只接收整条 `reasoning_content` 文本，不理解多轮工具调用。
  - 头部仍含非文本图标字符，且只适合单块思考内容。
- `frontend/src/features/chat/components/InlineToolCallCard.tsx`
  - 当前是独立卡片列表，不能附着到某个“思维链段”内部。
- `frontend/src/features/chat/components/AssistantExecutionDetails.tsx`
  - 当前单独展示“执行步骤 / 工具调用 / 用量信息”，和上面的工具卡片存在信息重复。
- `frontend/src/features/chat/types.ts`
  - 只有消息级模型：`ChatMessage`、`AssistantExecutionMeta`、`ToolEventMeta`。
  - 缺少“assistant 消息内部的分段模型”。
- 现有测试：
  - `frontend/src/__tests__/features/chat/ChatPage.test.tsx` 已覆盖流式 `status/plan/task/tool/chunk/usage` 混合事件。
  - `frontend/src/__tests__/features/chat/components/ReasoningContent.test.tsx` 已覆盖展开/折叠行为。

### 后端事件语义确认

- `frontend/src/shared/api/api.ts`
  - `sendMessageStream()` 会把 SSE 中的 `reasoning` 事件和 `chunk.reasoning_content` 统一转成前端 `type: 'chunk'`。
  - `tool` 事件和 `chunk` 事件是分开发送的。
- `backend/core/agent.py`
  - 后端流式处理支持多轮回环：某轮先输出 `content/reasoning_content`，再返回 `tool_calls`，工具执行后再进入下一轮 LLM 续写。
  - 说明“回复1 -> 新思考链 -> 工具调用2 -> 回复2”在后端能力上成立，问题仅在前端没有把事件重建成分段视图。
- `backend/tests/test_chat_streaming_status.py`
  - 已明确存在“先输出一段正文和思考，再 tool_call，再下一轮正文”的真实链路。

## Proposed Changes

### 1. 在消息类型中引入“段级视图模型”

- 文件：`frontend/src/features/chat/types.ts`
- 变更：
  - 为 assistant 消息新增内部段级类型，建议新增：
    - `AssistantMessageSegment`
    - `AssistantThoughtSegment`
    - `AssistantReplySegment`
  - 其中思维链段至少包含：
    - `id`
    - `kind: 'thought'`
    - `reasoningContent`
    - `toolEvents`
    - `steps`
    - `usage?`
    - `status`（例如 `running` / `completed`）
  - 回复段至少包含：
    - `id`
    - `kind: 'reply'`
    - `content`
- 原因：
  - 只有先把“消息”拆成“思维链段 + 回复段”，渲染层才可能按用户要求排序展示。
- 约束：
  - 尽量保留现有 `ChatMessage` 顶层字段，避免一次性重写历史缓存读取逻辑。
  - 新字段可增量挂到 assistant 消息上，例如 `segments?: AssistantMessageSegment[]`。

### 2. 新增分段构建器，统一把流事件重建为链路

- 文件：
  - 新增 `frontend/src/features/chat/utils/assistantSegments.ts`
  - 可能配套新增测试 `frontend/src/__tests__/features/chat/assistantSegments.test.ts`
- 变更：
  - 提供纯函数，负责根据当前消息状态和新事件更新 segments。
  - 需要覆盖的核心规则：
    - 初次出现 reasoning / tool / step 时，创建当前思维链段。
    - 工具调用始终挂到“当前未闭合的思维链段”内。
    - 当出现正文 chunk 时：
      - 若当前末段是回复段，则继续追加正文；
      - 若当前末段是思维链段，则在其后新建回复段并追加正文。
    - 当已经出现过回复段后，后续再次出现 reasoning / tool / step 时：
      - 新建下一个思维链段；
      - 该段与上一个回复段并列，形成 `思维链N+1 -> 回复N+1` 结构。
    - 若直到消息结束都没有正文：
      - 保持只有思维链段，不补空回复段。
    - `usage` 默认挂到最后一个思维链段；若不存在思维链段，再回落到消息级展示。
  - 需要同时处理直接模式：
    - 后端 direct 响应只有整段 `reasoning_content + response + toolEvents` 时，按同一套规则一次性构建 segments。
- 原因：
  - 把“按回复切段”的复杂状态机从页面组件中抽离，降低 `ChatPage.tsx` 的复杂度。

### 3. 调整 `ChatPage.tsx` 的事件归并逻辑

- 文件：`frontend/src/features/chat/ChatPage.tsx`
- 变更：
  - 在流式 `chunk / tool / task / plan / result / subagent_* / usage` 事件到达时，不再只更新 `messageMeta` 或直接拼接字符串。
  - assistant 消息更新分成两层：
    - 兼容层：保留现有 `content` / `reasoning_content` 更新，避免旧组件或缓存立即失效。
    - 新层：同步调用 `assistantSegments` 构建逻辑，把当前事件投影到 `segments`。
  - `messageMeta` 仍可保留作流式中间态来源，但其渲染职责下沉到段级模型中。
  - 处理 direct 模式时，收到 `response.data` 后一次性生成：
    - 第一段思维链（reasoning + toolEvents + steps + usage）
    - 若 `response` 非空，再生成第一段回复。
- 原因：
  - 当前问题根源在这里：页面把所有事件分别放入“整条 message”或“独立 meta”，没有为展示顺序建立状态机。

### 4. 将 `ChatMessage.tsx` 改为基于 segments 渲染

- 文件：`frontend/src/features/chat/components/ChatMessage.tsx`
- 变更：
  - assistant 消息不再使用固定顺序：
    - `ReasoningContent -> InlineToolCallCard[] -> MessageContent -> AssistantExecutionDetails`
  - 改为：
    - 遍历 `message.segments`
    - `thought` 段渲染为一个完整的思维链块
    - `reply` 段渲染为一个独立回复块
  - 兼容策略：
    - 若历史消息没有 `segments`，则从现有 `reasoning_content + toolEvents + content` 派生一个兜底结构，保证旧缓存和历史记录仍能显示。
- 原因：
  - 这是最终展示逻辑的核心落点。

### 5. 重构思维链内部展示，合并工具与执行详情

- 文件：
  - `frontend/src/features/chat/components/ReasoningContent.tsx`
  - `frontend/src/features/chat/components/InlineToolCallCard.tsx`
  - `frontend/src/features/chat/components/AssistantExecutionDetails.tsx`
  - 可能新增 `frontend/src/features/chat/components/AssistantThoughtSegment.tsx`
  - 可能新增或调整对应 `*.module.css`
- 变更建议：
  - 优先新增 `AssistantThoughtSegment.tsx` 作为段级容器，内部组合：
    - 思考文本
    - 执行步骤
    - 工具调用
    - 用量信息
  - `ReasoningContent.tsx` 可以保留其“可折叠思维链容器”能力，但 props 要从单纯 `content` 扩展到适配段数据，或只保留基础折叠壳能力后由新组件包一层。
  - `InlineToolCallCard.tsx` 保留可展开的参数/结果查看能力，但不再在消息主视图里单独平铺，而是作为思维链段内部子项。
  - `AssistantExecutionDetails.tsx` 不再作为 assistant 消息底部独立块；其“步骤 / 用量”展示能力迁移到思维链段内部，或降级为内部小节。
- 原因：
  - 用户已明确要求“工具调用包含在思考内”，因此这几个组件的职责边界必须重组。

### 6. 清理或下线重复的悬浮执行面板

- 文件：`frontend/src/features/chat/ChatPage.tsx`
- 变更：
  - 当前 `renderFloatingExecutionPanel()` 也会重复展示步骤和工具调用。
  - 既然产品已决定“并入思维链”，建议移除该浮层，或至少在有段级思维链展示时默认不渲染。
- 原因：
  - 否则页面会同时出现“思维链里的工具调用”和“悬浮执行面板”，导致重复信息和视觉冲突。
- 默认决策：
  - 实施时直接移除悬浮执行面板渲染；若依赖过大，则先保留函数但停止挂载，减少回归面。

### 7. 保留 `MessageContent.tsx` 仅负责回复渲染

- 文件：`frontend/src/features/chat/components/MessageContent.tsx`
- 变更：
  - assistant 场景下，不再让它承担“思考 / 文件 / 任务”解析入口。
  - 它应退化为“仅渲染 reply 段正文 markdown”的组件。
  - `parseStream()` 如果只服务旧格式思考解析，可逐步降级为兜底兼容逻辑，而不是主路径。
- 原因：
  - 当前它把思考与正文重新混在一个 `content` 字符串里解析，不适合新的显式段模型。

### 8. 更新测试，覆盖关键分段场景

- 文件：
  - `frontend/src/__tests__/features/chat/ChatPage.test.tsx`
  - `frontend/src/__tests__/features/chat/components/ReasoningContent.test.tsx`
  - 新增 `frontend/src/__tests__/features/chat/assistantSegments.test.ts`
- 需要覆盖的验收场景：
  - 单轮：`思考 + 工具调用 + 回复`
  - 双轮：`思考1 + 工具1 + 回复1 + 思考2 + 工具2 + 回复2`
  - 无回复：`思考1 + 工具1 + 思考2 + 工具2` 全都仍在思维链区域内
  - 工具后连续多个正文 chunk：合并为同一个回复段
  - direct 模式一次性返回 `reasoning_content + response + toolEvents`
  - 历史消息无 `segments` 时的兜底渲染
- 原因：
  - 当前已有测试只断言“都显示出来了”，还没有断言“显示顺序和分组关系正确”。

## Assumptions & Decisions

- 不改后端协议，完全在前端消费层和渲染层完成本次需求。
- 消息持久化和缓存短期继续兼容旧结构：
  - 继续保留 `content`、`reasoning_content`、`toolEvents`
  - 新增 `segments` 作为主展示数据
  - 历史记录未带 `segments` 时，前端运行时派生兜底结构。
- 回复边界定义：
  - 从某次工具调用结束后开始累积正文；
  - 累积到下一次新的 reasoning / tool / step 到来前，视作同一回复段。
- “无回复”定义：
  - assistant 消息在整轮执行结束后没有任何非空正文内容；
  - 此时只显示思维链段，不补空白回复块。
- 用量信息归属：
  - 默认归最后一个思维链段；
  - 若没有思维链段，则作为 assistant 消息尾部轻量信息兜底显示。
- 样式策略：
  - 优先复用现有 `ReasoningContent` / `InlineToolCallCard` / `ThinkingProcess` 的折叠与子卡片样式；
  - 避免重做整套视觉风格，只聚焦结构变化。

## Verification Steps

- 单元测试：
  - 运行 `frontend/src/__tests__/features/chat/assistantSegments.test.ts`
  - 更新并运行 `frontend/src/__tests__/features/chat/ChatPage.test.tsx`
  - 如继续保留 `ReasoningContent.tsx` 的折叠能力，更新并运行 `frontend/src/__tests__/features/chat/components/ReasoningContent.test.tsx`
- 类型检查：
  - 运行前端 TypeScript 检查，确保新增段模型和组件 props 无类型错误。
- 手工验收：
  - 流式模式下验证：
    - 第一轮工具调用前的思考与工具卡片在同一个思维链块中
    - 第一轮产生正文后出现独立回复块
    - 第二轮新的思考不会附着到第一轮思维链，而是在回复1之后新开思维链块
  - direct 模式下验证：
    - 一次性返回的 reasoning / tools / reply 仍按“思维链 + 回复”顺序展示
  - 历史消息验证：
    - 旧会话可正常显示，不因缺少 `segments` 崩溃或空白

## 实施顺序建议

1. 先补 `types.ts` 和 `assistantSegments.ts`，把分段状态机稳定下来。
2. 再改 `ChatPage.tsx`，把流式与 direct 两条数据入口都接入分段构建器。
3. 然后重构 `ChatMessage.tsx` 与思维链段组件，完成主视图切换。
4. 最后移除重复的详情/浮层展示并补测试。
