### 2.3 当前变更中发现的问题

#### 问题 1：数字输入清空时边界值处理不一致 【中优先级】
**位置：** `SettingsPage.tsx` `timeout`/`retry_count`/`max_tokens` 输入处理
**描述：** 当用户清空输入框时，`timeout` 被设为 `0`（后端要求 `>=1`），`max_tokens` 被设为 `0`（语义应为"使用默认值"）。
**建议：** 清空时应设为 `undefined` 或剔除字段，让后端使用默认值。
```typescript
// 当前实现（有问题）
onChange={(e) => { 
  const val = e.target.value; 
  if (val === '') { 
    updateModelEditParam(modelName, 'timeout', 0)  // 后端要求 >=1
  }
}}

// 建议修复
onChange={(e) => { 
  const val = e.target.value; 
  if (val === '') { 
    updateModelEditParam(modelName, 'timeout', 120)  // 恢复默认值
  }
}}
```

#### 问题 2：`toggleModelConfig` 函数中 `providerForm.provider` 闭包引用 【低优先级】
**位置：** `SettingsPage.tsx` `toggleModelConfig` 函数
**描述：** 函数内部通过闭包引用 `providerForm.provider`，但 `providerForm` 是 state。当 provider 切换时，已捕获的闭包值可能过时。
**建议：** 使用 `useRef` 存储最新的 provider 值，或使用函数式更新。

#### 问题 3：API 调用降级路径的重复代码 【低优先级】
**位置：** `SettingsPage.tsx` `toggleModelConfig` 函数
**描述：** try 块中的成功路径和 catch 块中的降级路径有大量重复的默认值赋值代码。
**建议：** 提取为共享函数 `getDefaultModelParams(config, caps)`。

## 3. 后端架构深度分析

### 3.1 Agent 核心流程

**文件：** `backend/core/agent.py`（2667 行）

#### 优点
1. **清晰的四阶段流水线：** `comprehension → planner → executor → feedback`，职责边界清晰
2. **魔法命令优先检测：** `_check_and_handle_magic_command` 在 LLM 调用前执行，避免不必要的 API 调用
3. **定时任务隔离机制：** `_apply_scheduled_execution_defaults` 为定时任务自动关闭行为日志、对话记录、记忆更新等
4. **活跃任务管理：** `_active_agent_tasks` 字典 + 容量上限 + 自动清理，防止内存泄漏
5. **CancelledError 正确处理：** 返回取消状态而非崩溃
6. **背压控制：** `_record_semaphore` 限制并发 fire-and-forget 记录任务数
7. **Agent 类型白名单校验：** `ALLOWED_AGENT_TYPES` 防注入

#### 问题

##### 问题 4：文件过大，职责过多 【高优先级】
**位置：** `backend/core/agent.py`
**描述：** 2667 行代码包含了流式处理、对话管理、上下文构建、能力注入、工具定义构建、子代理管理等多个职责。
**影响：** 可维护性下降，单文件修改风险增加。
**建议：** 按职责拆分为：
- `agent.py` — 核心流程编排（保留 ~500 行）
- `agent_streaming.py` — 流式处理逻辑
- `agent_capabilities.py` — 能力注入和工具定义构建
- `agent_context.py` — 上下文准备和管理

##### 问题 5：`MemoryManager` 使用 SessionLocal（工厂）但生命周期不明确 【中优先级】
**位置：** `agent.py:140`
```python
self.memory_manager = MemoryManager(SessionLocal)
```
**描述：** 传入 `SessionLocal`（`sessionmaker` 工厂）是正确的做法（避免跨请求共用 Session），但 AIAgent 实例化后 `memory_manager` 的生命周期与 Agent 实例绑定。在 SSE/WebSocket 长连接场景下，需要确保 MemoryManager 内部的 Session 管理正确。
**建议：** 在 `_closed` 标志检查中加入 memory_manager 的清理逻辑。

##### 问题 6：`_build_native_tools` 的 `seen_names` 去重未考虑 MCP 工具 【中优先级】
**位置：** `agent.py:625-649`
**描述：** `_build_native_tools` 只对插件工具去重（使用 `seen_names`），但后续添加的 MCP 工具和内置工具也使用相同的命名空间。如果插件工具名与 MCP 工具名冲突，后添加的工具会覆盖前者，但不会报错。此外，MCP 工具在第 650 行之后添加时没有检查 `seen_names`。
**建议：** 统一去重逻辑，对重复工具名记录告警日志。

### 3.2 执行层

**文件：** `backend/core/executor.py`（2006 行）

#### 优点
1. **工具调用参数校验：** `validate_parameters_against_schema` 基于 JSON Schema 校验
2. **幂等键机制：** 使用 `hashlib.sha256` 生成 `idempotency_key` 防止重复执行
3. **工具名前缀归一化：** 自动修正模型输出的大小写错误（`Plugin_` → `plugin_`）
4. **PreToolUse Hook：** 支持外部拦截/修改工具调用

#### 问题

##### 问题 7：与 PluginManager 的内部实现耦合 【中优先级】
**位置：** `executor.py:1420-1446`
```python
if not any(candidate in getattr(pm, "plugin_metadata", {}) for candidate in candidate_names):
    discovered = pm.discover_plugins()
```
**描述：** 使用 `getattr` 访问 `plugin_metadata` 和 `loaded_plugins`，这些是 `plugin_manager.py` 的内部属性。耦合度较高，如果 PluginManager 重构内部结构，执行器会静默失败。
**建议：** PluginManager 应提供 `has_plugin(name)` 和 `is_plugin_loaded(name)` 公开方法。

##### 问题 8：文件过大 【高优先级】
**位置：** `backend/core/executor.py`
**描述：** 2006 行包含 LLM 调用、工具执行、流式处理、子代理管理等多个职责。
**建议：** 拆分为 `executor.py`（核心）、`executor_llm.py`（LLM 调用）、`executor_tools.py`（工具分发）。

### 3.3 插件系统

#### 优点
1. **完整的生命周期状态机：** 8 状态 + 显式有效转换

**位置：** `backend/plugins/plugin_manager.py`
**描述：** 单体类 `PluginManager` 包含发现、加载、生命周期、热更新、执行、事件、配置等全部职责。这是项目中最复杂的文件。
**建议：** 拆分为多个协作类：
- `PluginDiscovery` — 发现和扫描
- `PluginLifecycle` — 生命周期状态机（已有 `plugin_lifecycle.py`，可进一步整合）

**文件：** `backend/memory/manager.py`（~800 行）、`backend/memory/experience_manager.py`（~600 行）

#### 已知问题（CLAUDE.md 已记录）
- **ExperienceManager 使用同步 SQLAlchemy 查询在 `async def` 中：** 可能阻塞事件循环
- **VECTOR_DB_PATH 相对路径：** 可能因工作目录变化而失效

### 3.5 数据库迁移

**文件：** `backend/db/models.py`

#### 优点
- 渐进式迁移：每个迁移函数独立，检查存在性后执行
- 使用 `inspect` 获取当前 Schema 状态
- 事务包裹（`target_engine.begin()`）
- 参数化查询防止 SQL 注入

#### 问题

##### 问题 10：迁移不支持回滚 【低优先级】
**描述：** 渐进式迁移模式不支持回滚，如果某次迁移出错，修复需要手动编写补偿 SQL。
**建议：** 考虑在 CI/CD 中增加迁移前的自动备份步骤（SQLite → `.backup`）。

##### 问题 11：多实例并发启动可能冲突 【低优先级】
**描述：** 多个 worker 同时启动时可能同时执行迁移。虽然 `IF NOT EXISTS` 保护了 DDL，但 `UPDATE` 语句可能重复执行。
**影响：** 低（当前为单实例开发环境）。

## 5. 安全审计

### 5.1 认证与授权

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 密码哈希 | ✅ | pbkdf2_sha256 (600K 轮) + bcrypt (12 轮) 兼容 |
| JWT 黑名单 | ✅ | jti + 数据库黑名单 + 自动过期 |
| Cookie 安全 | ✅ | HttpOnly + SameSite=lax |
| CSRF 保护 | ✅ | X-CSRF-Token + 自动引导 + 过期重试 |
| RBAC | ✅ | 三级角色 + 通配符权限 |
| 登录限流 | ✅ | 滑动窗口 + 容量保护 |

#### 发现的问题

##### 问题 16：登录限流在分布式部署中不共享 【高优先级】
**位置：** `backend/api/routes/auth.py:44-46`
**描述：** 限流状态存储在进程内存中的字典。多 worker/多实例部署时，限流状态不共享，攻击者可通过轮换请求到不同 worker 绕过限流。
**建议：** 实现 Redis 后端，或使用数据库存储限流状态（增加 `login_rate_limits` 表）。

##### 问题 17：RBAC 权限粒度不足 【低优先级】
**位置：** `backend/security/rbac.py:141`
**描述：** `check_permission` 使用精确字符串匹配，不支持通配符权限如 `skill:*`。目前只有 `admin` 角色拥有 `*` 通配符（全部权限）。
**建议：** 支持层级匹配，如 `skill:read` 可以匹配 `skill:*` 或 `skill:read`。

### 5.2 沙箱安全

| 检查项 | 状态 | 说明 |
|--------|------|------|
| 命令白名单 | ✅ | 14 个安全命令 |
| 命令黑名单 | ✅ | 28 个危险命令 |
| Shell 注入防护 | ✅ | `shlex.split()` + `create_subprocess_exec`（非 shell 模式） |
| 路径遍历防护 | ✅ | `resolve()` + `relative_to()` 校验 |
| 超时控制 | ✅ | `asyncio.wait_for` |
| SQL 注入防护 | ✅ | 全部使用 SQLAlchemy ORM 或参数化查询 |

#### 发现的问题

##### 问题 18：沙箱危险参数正则可能误伤合法参数 【低优先级】
**位置：** `backend/security/sandbox.py:42`
```python
re.compile(r'[;&|`$]'),  # Shell 特殊字符
```
**描述：** 此模式会拒绝所有含 `&` 的参数。对于需要使用 URL 参数传递的场景（如 `echo "http://example.com?a=1&b=2"`），`&` 会触发拒绝。
**建议：** 区分参数是作为命令参数还是数据传递。对于数据参数（如 `echo` 的参数），应放宽限制。

##### 问题 19：沙箱命令白名单过于严格 【低优先级】
**描述：** 仅 14 个命令（`ls`、`cat`、`grep`、`find`、`echo`、`pwd`、`head`、`tail`、`sort`、`uniq`、`wc`、`cut`、`mkdir`、`cp`、`mv`）。没有 `diff`、`git`、`du`、`df` 等常用的只读/低风险命令。
**建议：** 分类扩展白名单，区分"只读命令"和"写入命令"，前者可以更宽松。

### 5.3 敏感信息保护

| 检查项 | 状态 | 说明 |

| 优化项 | 位置 | 说明 |

| 上下文压缩 | `context/compressor.py` | 自动压缩对话历史 |

### 6.2 潜在性能问题

##### 问题 20：同步 ORM 查询在异步上下文中 【中优先级】
**位置：** `backend/memory/experience_manager.py`
**描述：** CLAUDE.md 已记录此已知问题。同步 SQLAlchemy 查询在 `async def` 中执行可能阻塞事件循环，高并发时影响吞吐。
**建议：** 迁移到 SQLAlchemy 2.0 异步 API（`AsyncSession`），或将同步查询放入 `run_in_executor`。

##### 问题 21：`_active_agent_tasks` 字典的锁竞争 【低优先级】
**位置：** `backend/core/agent.py:48`
**描述：** 全局字典的读写没有显式锁保护。虽然 asyncio 单线程特性降低了并发风险，但在 `await` 点之间仍可能被修改。
**建议：** 使用 `asyncio.Lock` 保护写操作，或使用 `contextvars` 替代全局字典。

##### 问题 22：`_build_native_tools` 每次请求重新构建 【低优先级】
**位置：** `backend/core/agent.py:625`
**描述：** 每次 `process` 调用都重新构建工具定义列表。如果会话内有多轮工具调用，这是不必要的重复计算。
**建议：** 在 `_inject_runtime_capabilities` 中缓存结果。
