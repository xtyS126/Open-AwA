## Bug 1: 登录后 CSRF Token 丢失导致 403 错误 [严重]

### 现象

前端大量请求返回 403，错误详情为 `"CSRF token verification failed"` 或 `"Request failed with status code 403"`：

| 时间 | 端点 | 状态码 | 详情 |
|------|------|--------|------|
| 09:44:48 | POST /api/conversations | 403 | CSRF token verification failed |
| 09:44:48 | POST /api/conversations | 403 | CSRF token verification failed |
| 09:45:04 | GET /api/coding/tree | 403 | (空) |
| 09:45:04 | GET /api/coding/cc-mode | 403 | CSRF token verification failed |
| 09:45:15 | GET /api/coding/read | 403 | CSRF token verification failed |
| 09:45:18 | GET /api/coding/git/status | 403 | (空) |

### 根因分析

**根本原因：登录成功后 `csrf_token` 被丢弃，未缓存到内存变量中。**

1. 后端 `POST /api/auth/login` 返回响应体包含三个字段：
   ```json
   {
     "access_token": "...",
     "token_type": "bearer",
     "csrf_token": "eyJ..."
   }
   ```

2. 前端 `LoginPage.tsx` 第 31-34 行只提取了 `access_token`，**完全忽略了 `csrf_token`**：
   ```typescript
   setAuth(
     { username: username.trim() },
     response.data.access_token || null  // ← csrf_token 被丢弃
   )
   ```

3. 前端 `api.ts` 的 `_cachedCsrfToken` 变量始终为空，导致每个状态变更请求（POST/PUT/DELETE/PATCH）都需要额外发起一次 `GET /api/auth/csrf-token` 来获取 token。

4. 在页面加载时，多个组件（Chat、Conversation、Coding）几乎同时初始化，多个 POST 请求并发执行。CSRF token 的引导请求与 API 请求之间产生竞态条件——Axios 拦截器中的 `ensureCsrfToken()` 是异步的，部分 POST 请求在 CSRF token 尚未返回时就已发出。

5. `/coding/*` 端点的空 detail 403 来自 `coding.py` 自身的目录访问控制（`_resolve_project_dir` / `_resolve_and_validate_path`），非 CSRF 中间件。

### 修复方案

**方案 A（推荐）：登录响应中直接缓存 CSRF token**

在 `LoginPage.tsx` 中提取 `csrf_token` 并缓存到 `api.ts` 的模块变量：

```typescript
// LoginPage.tsx
import { getCsrfToken } from '@/shared/api/api' // 需要新导出 setCsrfToken

const response = await authAPI.login(username.trim(), password)
// 缓存后端返回的 csrf_token，避免后续额外的引导请求
_setCachedCsrfToken(response.data.csrf_token || '')
```

同时在 `api.ts` 中导出 `setCachedCsrfToken` 函数。

**方案 B（辅助）：改进 ensureCsrfToken 竞态保护**

在 `api.ts` 的 `ensureCsrfToken` 中增加更完善的并发保护，确保多个并发调用共享同一个引导 promise。

### 涉及文件

- `frontend/src/features/auth/LoginPage.tsx` — 登录后缓存 csrf_token
- `frontend/src/shared/api/api.ts` — 导出 setCachedCsrfToken 方法
- （可选）`frontend/src/shared/store/authStore.ts` — 在 store 中维护 csrf_token

## Bug 2: User Profile Chat 插件配置验证失败 [中等]

### 现象

```
10:02:40 | WARNING | [user-profile-chat] 未知动作: unknown_action
10:02:40 | ERROR   | [user-profile-chat] max_messages_per_analysis 必须大于 0
```

### 根因分析

1. **未知动作**: `execute()` 方法收到 `action="unknown_action"`，不在支持的动作列表中（`analyze_user_profile`、`get_user_profile`、`on_chat_message`）。这可能是前端或定时任务传入了无效的 action 值。

2. **max_messages_per_analysis 必须大于 0**: 插件配置中 `max_messages_per_analysis` 被设置为 0 或负数。虽然 `__init__` 中有默认值 100，但 `validate()` 读取的是 `self.config` 中的实际值。如果插件配置文件或数据库中该值为 0，validate 会失败。

   查看 `index.py` 第 208 行：
   ```python
   self._max_messages: int = int(self.config.get("max_messages_per_analysis", 100))
   ```
   当配置值恰好为 0 时，`config.get("max_messages_per_analysis", 100)` 返回 0（非 falsy 的默认值不生效），导致 `_max_messages = 0`。

### 修复方案

1. **配置值防御性校验**：在 `__init__` 中增加对配置值的范围检查，无效值时回退到默认值：
   ```python
   raw_max = int(self.config.get("max_messages_per_analysis", 100))
   self._max_messages = raw_max if raw_max > 0 else 100
   ```

2. **未知动作增加详细日志**：记录调用方传入的完整 kwargs，帮助排查调用来源：
   ```python
   logger.warning(f"[{self.name}] 未知动作: {action}, kwargs: {list(kwargs.keys())}")
   ```

### 涉及文件

- `plugins/user-profile-chat/src/index.py` — 配置值防御 + 日志增强

## Bug 3: DeepSeek API Key 认证失败 (401) — 根因：加密存储后读取时未解密 [严重]

### 现象

```
10:14:18 | ERROR | 模型列表拉取失败: Client error '401 Authorization Required' for url 'https://api.deepseek.com/v1/models'
```

### 根因分析

**API Key 存储时经过 Fernet 加密，但读取时未解密，加密密文被直接作为 Bearer Token 发送。**

详细数据流：

1. **保存路径** (`pricing_manager.py:1154-1159`)：
   ```python
   if raw_key:
       from config.security import encrypt_secret_value
       normalized["api_key"] = encrypt_secret_value(raw_key)  # → "enc:gAAAAAB..."
   ```
   API Key 被 Fernet 加密后存入 `model_configurations.api_key` 列。

2. **LLM 调用路径** (`executor.py:838-839`) — **正确解密**：
   ```python
   from config.security import decrypt_secret_value
   api_key = decrypt_secret_value(raw_key)
   ```
   所以正常的聊天/Agent 调用能正常使用 API Key。

3. **模型列表拉取路径** (`billing.py:1042`) — **未解密 (BUG)**：
   ```python
   actual_api_key = request_api_key if request_api_key else (config.api_key if config else "")
   ```
   直接使用了数据库中的加密值 `enc:gAAAAAB...`，该字符串被当作 Bearer Token 发送给 DeepSeek，服务端返回 401。

4. **为什么有时能工作**：如果用户在输入框中重新输入了 API Key（明文），该值通过请求体传递给后端，`request_api_key` 为明文真值，绕过了数据库读取路径。

### 修复方案

在 `get_models_by_provider` 中，从数据库读取 API Key 时调用 `decrypt_secret_value` 解密：

```python
from config.security import decrypt_secret_value
db_api_key = config.api_key if config else ""
actual_api_key = request_api_key if request_api_key else decrypt_secret_value(db_api_key)
```

同时修复 `serialize_configuration` 中 `include_secret=True` 分支的解密问题（虽然当前未使用）。

### 涉及文件

- `backend/billing/routers/billing.py:1040-1046` — get_models_by_provider 解密 api_key
- `backend/billing/routers/billing.py:216-218` — serialize_configuration 解密 api_key

## Bug 4: 模型供应商 API Key 输入后不自动保存 [严重]

### 现象

用户在设置页面输入 DeepSeek API Key 后点击"获取模型列表"，API Key 仅通过请求体传递给后端用于当次拉取，但**不会自动持久化到数据库**。导致：
1. 每次刷新页面或重新打开设置，API Key 需要重新输入
2. 若 API Key 输入错误导致 401，用户无法进入"导入模型"步骤（导入步骤中有保存逻辑）
3. 用户必须额外点击"保存供应商配置"按钮才能持久化 API Key

### 根因分析

`SettingsPage.tsx` 中"获取模型列表"按钮（第 1921 行）直接调用 `fetchProviderModels` 并透传输入框中的 `api_key`，但**没有在调用前将 API Key 保存到配置中**：

```typescript
// 修复前：只传递 api_key，不保存
onClick={() => fetchProviderModels(providerForm.provider, providerForm.selected_models, true, {
    api_endpoint: providerForm.api_endpoint,
    api_key: providerApiKeyInputRef.current?.value.trim() || providerForm.api_key
})}
```

而 `fetchProviderModels` 函数内部也没有保存逻辑。API Key 的唯一持久化路径是：
- `handleSaveProviderConfig`（"保存供应商配置"按钮）
- `handleImportModels`（"导入选中模型"按钮）

用户预期在输入 API Key 后点击"获取模型列表"时自动保存，但现有流程要求两个独立操作。

### 修复方案

在"获取模型列表"按钮的点击处理中，**先异步保存 API Key 到配置，再发起模型列表请求**：

```typescript
onClick={async () => {
    const nextApiKey = providerApiKeyInputRef.current?.value.trim() || ''
    // 先保存 API Key 到数据库
    if (nextApiKey && providerForm.config_id) {
        try {
            await modelsAPI.updateConfiguration(providerForm.config_id, { api_key: nextApiKey })
            setProviderForm(prev => ({ ...prev, has_api_key: true }))
            if (providerApiKeyInputRef.current) {
                providerApiKeyInputRef.current.value = ''
            }
        } catch {
            // 保存失败不阻塞模型列表拉取
        }
    }
    // 再拉取模型列表
    fetchProviderModels(providerForm.provider, providerForm.selected_models, true, {
        api_endpoint: providerForm.api_endpoint,
        api_key: nextApiKey || providerForm.api_key
    })
}}
```

### 涉及文件

- `frontend/src/features/settings/SettingsPage.tsx` — "获取模型列表"按钮增加 API Key 预保存逻辑
