# 代码审查修复 Spec

基于 2026-06-21 全项目代码自主审查报告，制定本修复规范。修复按 P0 → P1 → P2 优先级推进，每批修复后运行测试验证。

---

## 修复原则

1. **最小变更**：只修复审查报告列出的问题，不做额外重构
2. **保留行为**：修复不能改变现有功能语义
3. **中文注释**：所有新增/修改注释必须中文
4. **禁止 emoji**：使用 `[DONE]`/`[Fix]`/`[NEW]` 等文本标记替代
5. **类型完整**：Python 函数完整类型标注，TypeScript 禁用 `any`

## P0 高危修复（安全与数据完整性）

### P0-1 终端端点无认证与命令白名单 [DONE]

**文件**：`backend/api/routes/terminal.py`

**问题**：
- 第 38-82、128-148 行 `/sessions` 与 `/sessions/{session_id}/execute` 端点未使用 `Depends(get_current_user)`
- `TerminalSession.execute` 无命令白名单，任意命令可执行
- `cwd` 参数直接来自用户查询参数，未做路径约束

**修复方案**：
1. 为 `/sessions` POST 和 `/sessions/{session_id}/execute` POST 添加 `user: User = Depends(get_current_user)` 依赖
2. 在 `TerminalSession.execute` 中添加危险命令黑名单（参考 `core/builtin_tools/terminal_executor.py:16-57`）
3. 对 `cwd` 查询参数做路径校验：必须位于允许的工作区根目录下，使用 `Path.resolve().relative_to()` 约束

**验证**：未认证请求应返回 401；执行 `rm -rf /` 等危险命令应被拒绝

### P0-2 SSRF 漏洞修复 [DONE]

**文件**：
- `backend/api/routes/weixin_skill.py` 第 899-913 行
- `backend/api/routes/system.py` 第 366-519 行

**问题**：
1. `weixin_skill.py`：`redirect_host` 来自上游响应直接拼接 URL，未校验是否在 `WEIXIN_QR_ALLOWED_DOMAINS` 白名单
2. `system.py`：`/connectivity-test` 端点 `base_url` 未做 SSRF 校验，可探测内网/云元数据

**修复方案**：
1. `weixin_skill.py`：在拼接 `poll_base_url` 前调用 `_validate_qrcode_url` 或新增 `_validate_redirect_host` 校验白名单
2. `system.py`：新增 `_validate_connectivity_url(url)` 函数，校验：
   - 解析 URL 主机名
   - 解析主机名为 IP，拒绝私有/回环/保留地址（参考 `core/builtin_tools/web_search.py:115-154`）
   - 拒绝云元数据地址 `169.254.169.254`
   - 强制 HTTPS（生产环境）

**验证**：传入 `http://127.0.0.1`、`http://169.254.169.254` 应被拒绝

### P0-3 TTS 上传安全 [DONE]

**文件**：`backend/api/routes/tts.py` 第 196-240 行

**问题**：`/api/tts/clone` 音频上传仅校验扩展名 `.wav`，未校验 MIME 类型，未设置文件大小上限

**修复方案**：
1. 添加 MIME 白名单校验：`audio/wav`、`audio/wave`、`audio/x-wav`
2. 添加文件大小上限：50MB（参考 `weixin.py` 的多媒体上传上限）
3. 添加 `Content-Length` 头校验

**验证**：上传超过 50MB 文件应返回 413；上传非 audio MIME 应返回 400

### P0-4 file_manager TOCTOU 漏洞 [DONE]

**文件**：`backend/core/builtin_tools/file_manager.py` 第 20-39 行

**问题**：`is_path_safe` 在路径不存在时直接返回 True，存在 TOCTOU 风险

**修复方案**：
1. 路径不存在时返回 False（保守策略）
2. 或者：对父目录做 `resolve()` + `relative_to()` 校验，确保未来创建的文件仍在允许目录内
3. 推荐方案 2：使用 `path.parent.resolve()` 校验父目录在允许根目录内

**验证**：传入不存在的路径应返回 False 或父目录校验通过才返回 True

### P0-6 流式 LLM 调用无超时 [DONE]

**文件**：`backend/core/executor.py` 第 1330-1342 行

**问题**：流式 LLM 调用未用 `asyncio.wait_for` 包装，连接 hang 住可永久阻塞

**修复方案**：
1. 用 `asyncio.wait_for` 包装流式生成器的首次响应
2. 或使用 `httpx.Timeout` 在客户端级别设置 read timeout
3. 推荐方案：在流式迭代中添加 per-chunk 超时（`asyncio.wait_for(chunk_future, timeout=step_timeout)`）

**验证**：模拟 LLM 服务 hang 住，应在超时后抛出 `asyncio.TimeoutError`

### P0-7 前端资源泄露 [DONE]

**文件**：
- `frontend/src/features/chat/ChatPage.tsx` 第 189-194、420-458 行
- `frontend/src/features/tts/components/VoiceCloner.tsx` 第 64-82 行
- `frontend/src/features/tts/ttsApi.ts` 第 88-126 行
- `frontend/src/features/coding/components/CodingChatPanel.tsx` 第 49-63 行

**问题**：
1. ChatPage 卸载时未调用 `chatStream.abortStream()` 取消流式请求，未清理子代理定时器
2. VoiceCloner `setInterval` 未在卸载时 `clearInterval`
3. ttsApi `synthesizeStream` 不支持 AbortSignal，未在 finally 中 `reader.releaseLock()`
4. CodingChatPanel 调用 `sendMessageStream` 未传 AbortSignal

**修复方案**：
1. ChatPage：在 `useEffect` cleanup 中调用 `chatStream.abortStream()` 和 `subagentSync.cleanupAllSubagentTimers()`
2. VoiceCloner：将 interval id 存入 ref，在 `useEffect` cleanup 中 `clearInterval`
3. ttsApi：`synthesizeStream` 添加 `signal?: AbortSignal` 参数，finally 中 `reader.releaseLock()`
4. CodingChatPanel：创建 `AbortController`，传 signal 给 `sendMessageStream`，卸载时 abort

**验证**：组件卸载后不应有 pending 网络请求；定时器不应继续触发

## 验证流程

每完成一个 P0/P1 修复批次后：

1. **后端测试**：`cd backend && pytest -x --tb=short`
2. **前端类型检查**：`cd frontend && npx tsc --noEmit`
3. **前端 ESLint**：`cd frontend && npx eslint "src/**/*.{ts,tsx}" --max-warnings=0`
4. **前端测试**：`cd frontend && npm run test`
5. **Emoji 扫描**：`grep -rP '[\x{1F300}-\x{1F9FF}]' backend/ frontend/src/`（应无匹配）

全部完成后运行完整测试套件：
```bash
cd backend && pytest -v --cov
cd frontend && npm run test:coverage
```
