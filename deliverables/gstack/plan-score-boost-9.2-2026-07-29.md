## 零、架构瘦身与成熟方案采用原则

10.0 不以功能数量或抽象层数量衡量，而以更少的权威状态、更小的自研维护面和更强的运行证据衡量。

| 能力 | 当前证据 | 决策 | 退出条件 |
|---|---|---|---|
| 插件热更新 | 历史上 `PluginManager._runtime_routes` 与 `HotUpdateManager` 同时保存 active/standby；当前兼容入口已委托给 `HotUpdateManager` | **已收敛**：`HotUpdateManager` 是唯一权威；只持久化可序列化发布描述，不复制运行时对象 | 源码扫描只剩一个状态容器；进程重建可恢复发布描述；同步/异步生命周期回滚通过 |
| Agent 理解与规划 | `ComprehensionLayer` 87 行关键词分类，`PlanningLayer` 295 行规则模板；主链路仍依赖二者 | **必须替代**：第一选择是复用现有 LiteLLM 模型原生工具调用，先不新增图运行时依赖；只有持久化图、暂停恢复等评测证明现有端口不足时才评估 LangGraph | 在同一任务集上达到工具、记忆、权限、SSE/WebSocket、恢复与延迟门禁后，一次性删除旧理解/规划层和模型判断前的关键词自动匹配 |

| 模型供应商调用 | 已由 LiteLLM 统一非流式、流式、模型发现和连接检查 | **保留成熟组件**：继续缩薄本地适配器，禁止恢复逐供应商客户端 | 所有模型调用只经一个端口，供应商特例仅为数据映射 |

| 前端 API 客户端 | 领域模块已拆分，`api.ts` 仅作兼容聚合 | **完成后删除残留备份**：先确认无引用，再移除 `.old` 等迁移残留 | 构建、类型检查和引用扫描均通过 |

执行约束：

1. 新依赖只有在能够删除更多本地代码、通过依赖审计并有可回滚迁移时才允许引入。
2. 不为本地与服务端场景分别维护两套长期实现；差异通过端口和配置表达。
3. 兼容层必须是薄委托，并附带删除日期或明确退出门禁。
4. 评分只采纳已落地且已验证的删减，不把“计划采用成熟项目”计入完成分。

#### 用量发现与防回流控制

1. 静态扫描：每次 Agent、调度、插件或 store 变更时扫描旧类型、旧构造器和第二状态容器；新增命中必须阻断。
2. 运行证据：为旧 Agent 路径、调度扩展点与旧状态源增加临时命中计数；仅凭“代码搜索没有引用”不能删除动态入口。纯占位模块必须同时证明不存在动态导入、生命周期接线和持久化对象。
3. 完成粒度：按调用方、任务类型和持久化对象记录迁移完成，不能用“测试总数通过”替代 mixed-state 关闭证明。
4. 例外：只有明确负责人、原因和到期日的兼容读取可暂留；旧路径不得再接受新写入或新任务。
5. 禁用先于删除：旧入口先进入不可新建、只读或隔离状态，观察至少一个代表性业务周期，再删除代码、配置、凭据、告警、文档和成本工件。
6. 回流门禁：新增 `ComprehensionLayer`、`PlanningLayer`、第二 `AsyncScheduler`、第二插件状态容器、LanceDB、ZMQ 或第二桌面后端的生产引用应由架构测试直接失败。

#### 替代方案准入标准

- **删码比**：新增依赖及适配代码必须能删除更多本地生产代码；只换名字或增加一层包装不准入。
- **契约覆盖**：权限、审计、取消、恢复、SSE/WebSocket、多用户隔离和数据迁移必须有同一任务集证据。
- **运行成本**：依赖审计、冷启动、内存、尾延迟和故障面不得明显恶化。
- **可撤回**：在旧路径删除前可以按迁移批次回退；旧路径删除后使用版本回滚和数据兼容读取，不保留永久双写。
- **成熟度不等于适配度**：参考项目的组件只有在符合 Open-AwA 的多用户、服务器中心定位时才采用；本地单用户项目的便利方案不得直接复制。

当前明确不采用的“成熟替代”包括 LanceDB、ZMQ、第二插件框架和桌面端第二套内嵌后端。它们解决的是不同部署定位，放入当前多用户平台会制造双数据面、双调度面或双运维面，不能计为质量提升。

### 本轮对“成熟替代”的校正

成熟方案不是看到同类项目用了某个框架就复制，而是先判断当前代码到底是运行中的自研系统、仅有元数据的抽象，还是根本没有接入生产的占位实现。本轮复核得到以下校正：

| 发现 | 静态证据 | 决策 | 对评分的意义 |
|---|---|---|---|
| Bilibili 第二调度器并未进入生产 | 构造调用只在模块自身和测试；插件 `initialize()` 未创建它；执行入口明确是 placeholder | 已删除假实现，没有做“迁移到核心”式过度工程 | 私有调度包、专属占位测试和虚假能力面已归零 |
| 调度扩展协议只是登记簿 | `register_scheduler` 有写入，没有生产执行消费者 | 已删除扩展类型、schema 与文档入口，禁止继续扩展 | 消除“抽象存在即能力存在”的评分幻觉 |
| `data.collector` 是历史 no-op | 启动、关闭、流式 finalize 和工具执行后处理只有空调用或噪音 | 已删除整个生命周期占位并增加禁止复生测试 | 每次请求与每次进程生命周期少一条无意义路径 |
| 核心调度成熟替代已经完成 | `ScheduledTaskManager` 使用 APScheduler 触发、持久化和跨 worker 领取 | 保留并缩薄包装，不再引入第二框架 | 复用成熟能力但保持单一状态权威 |

上述退役项已经由“禁止复生”架构测试保护。生产源码对 `ComprehensionLayer`、`PlanningLayer`、`data.collector` 和 Bilibili 私有调度器的引用为 0；旧文件物理不存在；前端生产构建不再生成预压缩副本。

当前可证明综合分为 **9.24 / 10**，后端能力组约 **9.24 / 10**，前端能力组约 **9.21 / 10**。本次上调只计入已物理退役的旧实现、全量测试、全新服务三传输和真实 Chromium 证据；有效 provider 凭证、执行器继续缩薄、开发工具链 high 与长期运行数据仍阻断 10 分。

## 四、验证闭环（遵守 AGENTS.md §3）

每项代码改动必须走 6 步闭环：读记忆 → 规划 → 实现 → pytest/vitest → 服务+E2E → 沉淀记忆。
- 单步失败最多自愈 3 次，超限停止上报
- 不 push 远程；commit 仅在验证全绿后
- AST 架构测试（方法 ≤80 行、参数 ≤8、扇出 <15）为硬性门禁

## 六、风险与回滚

| 风险 | 缓解 |
|------|------|
| executor.py 拆分引入回归 | 拆分为纯移动（不改逻辑），门面类保持签名；每拆一组跑相关测试 |
| api.ts 拆分破坏引用 | barrel 文件 re-export 全部命名空间，引用方零改动；tsc 构建验证 |
| 热更新收敛影响插件状态机 | 先以一致性与重启恢复 RED 测试锁定契约；迁移中只允许短时兼容委托，不保留两个状态容器 |
| 引入成熟 Agent 运行时反而增加复杂度 | 先跑同一评测集；候选不能删除旧代码或无法覆盖恢复/权限/传输契约时不引入 |
| 服务重启导致浏览器验证环境缺失 | bin/dev.bat 或手动启动 backend(8000) + frontend(5173)，验证前 /api/system/ping 探活 |
